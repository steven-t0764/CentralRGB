# Review: no black flashes on restore or section switch (PR #29)

Reviewed: `main` at `cc9004a` (merge of PR #29, change commit `1cec327`), for Vizor issue #28.
Reviewer: Fabian. Read-only on product code: only this report is committed.

## Verdict: needs changes

The code change is small, readable, and matches the cause the PR describes. The automated checks pass and the
frames captured under Xvfb show no black window and no black boxes. I'm still not calling it ready, for three reasons:

1. **The PR description breaks the identity rule.** It ends with a "Generated by Claude Code" footer (finding 1).
2. **There's a likely side effect on the FPS overlay.** The new panel-colour class brush applies to every Tk window in the process, including the see-through FPS overlay (finding 2).
3. **Nothing here shows the Windows black flash is gone.** Xvfb can't reproduce the bug: the new frame check also passes on the *old* code. `tests/test_repaint.py` fails on the old code only because the new names (`OPAQUE`, `THAW_FLAGS`, `panel_background`) don't exist yet, not because of what the old code did (finding 3). The real-PC check is still to do. Earlier fixes (b1ec458, fix-restore-flicker) also passed here and failed on the real PC.

Findings 1 and 2 are defects that a follow-up task should fix. Finding 3 needs a run on the real Windows PC.

### What the frames show

- **Restore (66 frames):** after the first frame (bare desktop, before map), every frame is the complete Home page in the panel colours. There's no black window, no black boxes and no half-drawn frame.
- **Switching between every section (60 frames, all 8 pages):** no black at any point. Some frames show a page partly drawn: empty panel-coloured cards on Lighting, Settings and Fans for one or two frames before their contents appear. ## Does the stated cause match the code?

Yes, as far as it can be checked without Windows:

- **`_fade_in` now stops at `fx.OPAQUE`** (254/255 on Windows, 1.0 elsewhere), in `central_rgb.py` `App._fade_in`. When `-alpha` is set to exactly 1.0, Tk on Windows removes `WS_EX_LAYERED` and redraws the window with an erase. Keeping 254/255 avoids that. The self-test's `alpha >= 0.99` check still passes (0.996). The other alpha writes (`_reveal`, `_tray_action`, `_switch_theme`) all hand over to `_fade_in` at the end, so none of them leaves the window at 1.0.
- **`thaw()` now uses `THAW_FLAGS = RDW_INVALIDATE | RDW_ALLCHILDREN | RDW_FRAME`** (no `RDW_ERASE`, no `RDW_UPDATENOW`). All three callers (`show_page`, `_resize_done`, and `_switch_theme` through the page code) call `_paint_now()` (`self.update()`) right after, so the repaint still happens straight away and in one go.
- **`panel_background()`** sets `GCLP_HBRBACKGROUND` to a brush in `P["BG"]` on the outer window and on Tk's child class. It's called from `_window_effects`, which runs again after a theme switch, and it frees the previous brush. It does nothing off Windows.

The claim that "Windows keeps the picture of a layered window through minimize/restore" sounds plausible, but I couldn't verify it here.

## Findings

1. **PR #29 description: forbidden attribution line.** The body ends with `Generated by [Claude Code](https://claude.ai/code)`. CLAUDE.md forbids any "Generated with Claude Code" or Claude/Anthropic line in PR descriptions.
   *Fix:* edit the PR #29 description to remove the footer. Make sure future worker PRs leave it out too: the repository rule takes precedence over the tool's default footer.

2. **`win_effects.py` `panel_background()`: the class brush reaches the FPS overlay and other Tk windows.** `SetClassLongPtrW(GCLP_HBRBACKGROUND)` changes the *window class*, and every Tk window in the process shares it. That includes `fps_overlay.OverlayWindow` (a `tk.Toplevel` created by the app), the `PresetEditor` and the self-test's game window. The overlay relies on `-transparentcolor` `#010102`. Before this change the class had no brush, so Windows left the area alone. Now, whenever Windows clears the overlay before Tk draws it (when it's shown, moved, resized, or the game changes mode), it fills that area with the panel colour, not the see-through key colour. The result can be a solid panel-coloured rectangle flashing over the game for a frame. Not reproducible on Linux, but it follows from how window classes work.
   *Fix:* pick one of these:
   - Have the overlay handle `WM_ERASEBKGND` itself, or set the overlay's own `HWND` to a key-colour brush. Setting a brush per window isn't possible, but the overlay can be subclassed, or its `WM_ERASEBKGND` answered.
   - Better: don't change the class brush at all. On the main window only, answer `WM_ERASEBKGND` with a fill in the panel colour, so the overlay keeps its old behaviour.
   - Add a test asserting that `panel_background` doesn't affect windows other than the main one, or at least a Windows self-test step that shows the overlay and checks a pixel where the overlay should be see-through.

3. **`tests/test_repaint.py` / `tests/restore_check.py`: the tests can't show that the Windows bug is fixed.**
   - Under Xvfb, `NoBlackFramesOnRestoreOrSwitch` passes on the old code too. Xvfb has no DWM, no layered windows and no `RedrawWindow`.
   - The unit tests check constants (`THAW_FLAGS`, `OPAQUE`), not behaviour. For example, putting `RDW_ERASE` back inline in `thaw()`, without going through `THAW_FLAGS`, would still pass.
   - On Windows CI the frame test is skipped: `_gui_available()` needs `CENTRALRGB_GUI_TESTS=1`, and `build.yml` doesn't set it.

   The PR says all of this openly under "Not verifiable here", but that leaves the bug's real acceptance criterion unchecked. The issue says the earlier fixes passed here too and failed on the real PC.
   *Fix:*
   - (a) Run `python tests/restore_check.py out` on the real Windows PC and attach `restore.gif` and `switch.gif` to issue #27.
   - (b) Optionally, set `CENTRALRGB_GUI_TESTS=1` for the unittest step in `build.yml`, so the frame check also runs on the Windows runner. It has a desktop session, though it may not reproduce the 240 Hz behaviour.
   - (c) Make `test_thaw_does_not_erase` check the flags `thaw()` actually passes to `RedrawWindow`: patch `ctypes.windll` with a fake and read the call's argument.

4. **Minor: `restore_check.py`'s "much blacker than before" INFO line counts the pre-map frame.** It reports "much blacker than before minimizing: 1 (at ms [0])" on every Xvfb run. That's the bare desktop frame, which the new black-box check already skips.
   *Fix:* apply the same `since=mapped` cut-off to the `blackish` list, so the INFO line isn't misleading.
